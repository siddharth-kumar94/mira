# Capabilities

Last verified: f064d7ee53a4 on 2026-10-20 (live)

Rally Capabilities, above your teams' features (spec §16 #12): the list (`/initiatives`, tabs Active, Planned, All capabilities) and a capability page (`/initiative/<key>`, tabs Overview, Activity, Features). Read-only apart from updates, comments and priority (D23, D38): no New capability and no editing of status, owner or target. PMs use it. It lives in `web/src/pm/InitiativesList.tsx` and `InitiativePage.tsx` over `server/app/rally/portfolio.py`. Overall: beta. The list matches Rally's counts and the user's named capabilities show their features, rollup and health pills, but the read takes 11 s cold and the page showed features without health while it loaded.

## How to get to it (user POV)

1. In the sidebar, under "Workspace", open "Capabilities". It opens on "Active".
2. "Planned" and "All capabilities" change the tab. A click on a row opens the capability; the "n / total" button opens its Features tab and the health controls open its updates.
3. On the page, "Overview", "Activity" and "Features" switch the tab.
4. Display › Grouping › "Initiative" groups the list by Rally's Program.

## Driving it

Preconditions: baseline, then `rallypoc seed`. Allow up to 45 s for the first load.

- **initiatives-list**, **initiatives-health-pills**, **initiatives-page**: → `rallypoc browser run initiatives` → PASS: Capabilities › All shows the [DEMO] capability with "0 / 2" and its page has three tabs.
- **initiatives-status**, **initiatives-health-auto**: → `rallypoc check api` → `api:initiatives-read` PASS (1 [DEMO] capability).
- **initiatives-group-initiative**: not driven in a browser. `rallypoc api GET "/api/initiatives?teams=<ids>"` → each capability carries `parent_group_id` and `parent_group_name`.
- **initiatives-priority**: not driven (no field).

## Gotchas

- **The read is slow.** `GET /api/initiatives` took 11 s cold on 2026-10-20 (7 to 10 s in earlier runs); "Loading capabilities…" shows meanwhile. The same call is under a second for a minute afterwards.
- **A cold capability page used to show "No updates" briefly.** Opening `/initiative/<key>` on a fresh page, the embedded feature rows read "No updates" for over 16 s, then switched to "At risk" and "Off track". Cause: story-side reads (bootstrap, team, sprint) carry features without health and overwrote the PM reads' copies. Since `6a26fb3` a health-less copy keeps the health it had, and a feature whose health has not been read yet shows a blank chip, not "No updates" (`web/src/store/store.ts:252`, `web/src/components/pm.tsx:48`).
- **The [DEMO] capability cannot show a health change.** Its Features read "No status" (Backlog category), so it has no active features, and Rally's work rules stop the seed from starting them. An update on a [DEMO] Feature moves the Feature's own health everywhere except this capability's header (spec §14 scenario 7).
- **The [DEMO] capability has no Rally state.** The API reports its state as "No status", and its page shows the status Planned.
